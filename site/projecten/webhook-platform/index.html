Webhook-platform

Events betrouwbaar afleveren bij servers die traag zijn of uitvallen.

Python · FastAPI · PostgreSQL · Redis · Docker · React 18 · TypeScript · TanStack Query

Probleem

Een applicatie die klanten op de hoogte houdt van gebeurtenissen (een bestelling is aangemaakt, een betaling is mislukt) moet de servers van die klanten aanroepen. Die servers zijn soms traag, soms offline en soms verkeerd ingesteld.

Wacht de applicatie zelf op die aanroep, dan blokkeert ze de gebruiker. Probeert ze het niet opnieuw, dan gaat de gebeurtenis verloren. En zonder logboek kan niemand achteraf bewijzen wat er verstuurd is.

Wat ik gebouwd heb

  • Een API: de applicatie stuurt één event door en krijgt meteen 202 Accepted terug.
  • Een achtergrondproces dat het event naar elk geregistreerd adres stuurt, ondertekend met HMAC-SHA256 en een tijdstempel, zodat de ontvanger kan controleren wie de afzender is.
  • Automatisch opnieuw proberen na 1, 5 en 30 minuten. De status staat in PostgreSQL, dus bij een herstart gaat er niets verloren.
  • Een React-dashboard dat afleveringen, mislukkingen en nieuwe pogingen toont, met een demo-modus die zonder server werkt.
  • Dezelfde API opnieuw gebouwd in C# met ASP.NET Core 8 en EF Core (ms-webhook-api-dotnet): zelfde routes en JSON, 70 testgevallen, en het dashboard is er in een browser tegen gecontroleerd. Geen belastingtest, niet gedeployed, en de tests draaien op SQLite, niet op PostgreSQL.
  • Beveiliging: adressen naar interne netwerken worden geweigerd (SSRF-controle), API-sleutels worden gehasht opgeslagen en elke klant mag maximaal 100 events per uur versturen.

Hoe het werkt

  1. Event ontvangenPOST /events, gevalideerd en bewaard in PostgreSQL
  2. WachtrijRedis, de API antwoordt direct 202
  3. Afleveringhet achtergrondproces stuurt een ondertekende POST naar elk adres
  4. Resultaat bewaardgeslaagd, of nieuwe poging gepland na 1, 5 of 30 minuten
  5. Dashboardtoont elke poging met fout en tijdstip

Resultaat

Gemeten
Lokaal met Docker: ik stuurde een event naar een ontvanger die de eerste poging liet mislukken. De tweede poging kwam na ongeveer 60 seconden aan en de aflevering stond daarna als geslaagd, na twee pogingen. 10 automatische tests en CI groen.
Nog niet gedaan
Geen belastingstest, dus ik weet niet hoeveel events per seconde dit aankan. Het achtergrondproces draait in dezelfde applicatie en niet als aparte dienst. De demo draait op gratis hosting, waardoor de eerste aanvraag een halve minuut kan duren.

Wat mijn eigen controle opleverde. Toen ik de installatie-instructie vanaf een verse kloon volgde, werkte ze niet: de applicatie crashte bij het opstarten door een instelling, de container zocht de database op het verkeerde adres, 9 van de 10 tests faalden door een instelling van de testomgeving en de CI draaide niet op de standaardbranch. Ik heb dat opgelost in een pull request en de instructie aangepast.
