Projects / case study

Webhook platform

Delivering events reliably to servers that are slow or down.

Python · FastAPI · PostgreSQL · Redis · Docker · React 18 · TypeScript · TanStack Query

Problem

An application that notifies customers of events (an order was created, a payment failed) has to call those customers' servers. Those servers are sometimes slow, sometimes down and sometimes misconfigured.

If the application waits for that call itself, it blocks the user. If it doesn't retry, the event is lost. And without a log, nobody can later prove what was sent.

What I built

  • An API: the application sends one event and gets an immediate 202 Accepted.
  • A background process that sends the event to every registered address, signed with HMAC-SHA256 and a timestamp so the receiver can verify the sender.
  • Automatic retries after 1, 5 and 30 minutes. The state is in PostgreSQL, so a restart loses nothing.
  • A React dashboard that shows deliveries, failures and retries, with a demo mode that works without a server.
  • Security: addresses pointing to internal networks are refused (SSRF check), API keys are stored hashed and each customer is limited to 100 events per hour.

How it works

  1. Event comes inPOST /events, validated and stored in PostgreSQL
  2. QueueRedis; the API answers 202 straight away
  3. Deliverybackground process sends a signed POST to each address
  4. Result storedsucceeded, or a new attempt scheduled after 1, 5 or 30 minutes
  5. Dashboardshows every attempt with its error and time

Result

Measured
On a local Docker setup: an event was sent to a receiver that failed the first attempt. The second attempt arrived after about 60 seconds and the delivery then showed as succeeded, with two attempts. 10 automated tests and green CI.
Not yet
No load test, so I don't know how many events per second this can handle. The background process runs inside the same application, not as a separate service. The demo runs on free hosting, so the first request can take half a minute.

What my own check found. When I followed the project from a fresh clone, the install instructions didn't work: the application stopped at startup because of a setting, the container looked for the database at the wrong address, 9 of 10 tests failed because of a test-environment setting, and CI didn't run on the default branch. I fixed that in a pull request and corrected the instructions.
