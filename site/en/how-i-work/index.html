Approach

How I work

I build with an AI assistant and only believe what it produces once it has been tested.

In short

I use Claude Code as a tool to write, research and tidy up code faster. I treat what the assistant produces as a first draft: I read it, run it and test it. I decide what goes into the code and I can explain what it does.

The reason is simple: an assistant writes fluently and convincingly, even when something is wrong. Without checking, you quickly get more code, but also more mistakes nobody sees.

How it goes

  1. Goal and limits firstwhat it should do, and what it deliberately shouldn't
  2. Build in small stepswith the assistant, every step read and run
  3. A failing test firstonly then the fix, so I'm sure the bug was real
  4. Standing checkstests, style checks, a scan for secrets and for known vulnerabilities in dependencies
  5. Independent reviewseveral AI reviewers, each with a different role: security, claims, code quality, first impression
  6. Measure and write it down honestlywhat was measured, and what hasn't been done yet

What it produced

Measured
For the knowledge assistant, all 9 problems I reproduced with a failing test turned out to be real. For the data quality tool it was 19 of 22 (the other 3 tested behaviour that was already correct). Without that check, deleted documents would still have produced answers and approving a proposal could have merged two different companies.
Not yet
I haven't worked in a team yet: code review by colleagues, a long maintenance period and agreements with a client are things I haven't experienced. That's what I want to learn first.

A worked example is in the knowledge assistant case study: a measurement that looked perfect and, on a closer read, wasn't.
